### DEC-002 Term corrections are a substitution pass over pipeline output, from a hand-authored list
- **Added:** 2026-08-12 19:42 MST
- **Status:** RESOLVED (2026-08-12 19:15 MST)
- **Decided:** 2026-08-12
- **Question:** "Pre-render commonly misspelled words" could mean biasing the recognizer (`word_boost`), constraining the analyzer prompt, or generating a term list by scanning the TRFA repos. Which?
- **Answer:** None of those. Cenay: a **hand-authored** list of common terms, their common mishearings, and the correct value, applied as a **substitution over the transcription output**. This is Layer 3 of [`plans/term-normalization.md`](../plans/term-normalization.md).
- **Why:** The meetings are between teammates on a fixed set of TRFA projects, so the vocabulary is known in advance and stable — authoring beats generating. And the correction must reach the artifact, not just the recognizer.
- **Build impact:** `config/terms.yml` + `scripts/terms.py`. The list is one-to-many (`correct` → many `heard` variants), and variants can span word boundaries.

> **TL;DR —** Misheard words are fixed by a hand-written list of correct terms and the ways they get misheard, applied as a find-and-replace over the finished transcript — not by trying to teach the speech recognizer. The speakers are the same people discussing the same projects, so the vocabulary is known in advance, and the correction has to reach the saved file rather than just the recognizer.

### DEC-005 One flat term table; the CODE classifies risk, not the author
- **Added:** 2026-08-12 19:42 MST
- **Status:** RESOLVED (2026-08-12 19:15 MST)
- **Decided:** 2026-08-12
- **Question:** Some mishearings are made of ordinary English words (`book he`, `booking`). How are those matched without corrupting normal prose?
- **Answer:** One flat table — a `correct:` term plus a growable list of `heard:` strings. `scripts/terms.py` classifies each variant **at load time**: every token ordinary English → refused; any token a non-word → applied. A per-entry `force:` list overrides a refusal.
- **Why:** **Authoring cost is the binding constraint.** Cenay's requirement was *"a table I can add to over time as I discover things"*, so adding a row must cost nothing but the string. A hand-flagged safe/risky tier was rejected because it puts an invisible judgement call on every row, and that is how lists stop being maintained. Measured against 83 cached transcripts: `booking` appears **259 times**, nearly all legitimate — a replace-everything design would corrupt prose at scale.
- **Build impact:** ⚠️ **The classifier rule is more specific than it sounds, and was wrong on first specification.** A plain dictionary lookup refuses `book io` (because `io` is in `/usr/share/dict/words`); a minimum-token-length repair then wrongly *accepts* `book it` and `book he`. The verified rule is **dictionary lookup for 3+ character tokens plus an explicit stop-word set for 1–2 character tokens** — 19/19 cases correct. Do not simplify it back. Guarded by `tests/test_terms.py`.

> **TL;DR —** The correction list is one flat table anyone can add a row to, and the program decides which entries are risky rather than the author. A misheard phrase made only of ordinary English words is refused automatically unless explicitly forced, because judging each row by hand is how a list stops being maintained. One such word appears 259 times across the saved transcripts, nearly all of them legitimate.

### DEC-008 `/add-term` will auto-commit its one file — an exception to the no-auto-commit rule
- **Added:** 2026-08-12 19:42 MST
- **Status:** RESOLVED (2026-08-12 19:15 MST) · **not yet built**
- **Decided:** 2026-08-12
- **Question:** Terms are discovered while reviewing a meeting reconciliation in *another* repo. How does one get added, and what happens to the resulting uncommitted change here?
- **Answer:** A global `/add-term` command (`~/.claude/commands/`) backed by `claude-personal-toolkit/scripts/add-term.py`, writing to this repo's `config/terms.yml` by absolute path, plus a prompt in the `meeting-reconcile` skill to offer it when a term is corrected. **It commits and pushes that one file automatically.** It **fails loudly** with the path it tried if the file is absent, and never creates a fresh one.
- **Why:** The no-auto-commit rule exists because changes are tested before they are committed; a term addition has no such window — it is data, not code, and left uncommitted it sits unnoticed in a repo nobody is working in for weeks while the correction silently never applies. **Here, not committing is the failure mode rather than the safeguard.** A silently-created empty term list would apply zero corrections while every run reported success.
- **Build impact:** Scope is exactly one file — never `-a`, never a sweep of whatever the other repo left dirty. **The exception is recorded in the global `~/.claude/CLAUDE.md`**, because a session in another repo reads that file and would otherwise treat the behaviour as a bug.

> **TL;DR —** The command that records a newly discovered misheard term commits and pushes that one file by itself, against the usual rule. Terms get spotted while working in a different project, so the change would otherwise sit unnoticed for weeks in a repository nobody has open, and the correction would silently never apply.

### DEC-009 The analysis stage is protected TWICE — a prompt constraint and a post-pass, and the gap between them is the measurement
- **Added:** 2026-08-13 12:45 MST
- **Status:** RESOLVED (2026-08-13 12:22 MST) · closes the session desk's Q2
- **Decided:** 2026-08-13
- **Question:** Correcting the transcript does not stop Claude from *constructing* a wrong identifier (`bookio_product_groups`) in the summary — the stage where the original incident actually did its damage. Constrain the prompt, correct the output, or both?
- **Answer:** **Both.** `terms.py::spelling_constraint()` renders the term list into `ANALYSIS_PROMPT` (`analyzer.py:24`, one insertion point per [DEC-002]'s survey), and `terms.py::correct_structure()` walks the returned JSON in `pipeline.py` after the error guard. The post-pass **should normally find nothing**, and a non-empty result is logged loudly as a signal rather than a routine fix.
- **Why:** The two mechanisms fail in opposite directions, which is why neither alone is sufficient. A prompt constraint is **advisory** — the model may disregard it — but it has no failure mode: if a term entry is wrong, the model simply ignores a bad instruction. A substitution over model output is **guaranteed** but rewrites a decision record silently when a term entry is wrong. Doing both converts the tension into an instrument: **the residual count measures how well the constraint held.** This adopts the plan's argument over the position originally taken on the desk, which had recommended the post-pass alone.
- **Build impact:** `spelling_constraint()` is generated from `config/terms.yml`, so the prompt can never drift from the term list — adding a term updates both defenses. ⚠️ **`ANALYSIS_PROMPT` now takes a second `.format()` key**, which broke `scripts/diagnose_analysis.py` (a separate caller of the shared constant) with `KeyError: 'spelling'`; fixed in the same change. ⚠️ `correct_structure()` corrects dict **keys** as well as values — currently harmless because keys are fixed schema names, but a term colliding with a schema key would break the Notion renderer's lookups. `_usage` is skipped. Verified by stubbing the Claude call with a poisoned analysis and running the real `process_video()`; 19 new assertions in `tests/test_terms.py` (75 total, 0 failures). ⚠️ **The constraint half is unverified against a live model** — what is proven is that it renders and reaches the API payload. The post-pass is the net underneath it either way.

> **TL;DR —** Fixing the transcript does not stop the summary step inventing a wrong name of its own, which is where the original damage was actually done. So it is guarded twice: the correct spellings are handed to the summarizer up front, and its output is swept afterwards. The sweep should normally find nothing, and anything it does find is reported loudly as a signal rather than a routine fix.

### DEC-010 The corrections also go on the Notion page, in a toggle directly under the transcript
- **Added:** 2026-08-20 11:37 MST
- **Status:** RESOLVED (2026-08-20) · closes the session desk's Q6, the last open half
- **Decided:** 2026-08-20
- **Question:** [DEC-006] put every substitution in `logs/term-corrections.log`. Do the corrections *also* appear on the Notion page, and if so where?
- **Answer:** **Yes — a collapsed Heading 3 toggle titled `🔤 Term corrections applied by the pipeline`, placed immediately below the existing Transcript toggle.** Cenay: *"place the corrections in a similar toggle as the transcript (can live right below it) that states the correction."* It carries both passes — the transcript substitutions and any analysis-stage residual from [DEC-009] — each as `"heard" → Correct — N×`, with forced entries marked and the analysis rows grouped under their own warning that the model wrote them. `logs/` keeps its copy; the two serve different readers.
- **Why:** The page is not an output, it is the **interface to `meeting-reconcile`** — that session reads the page and never sees this repo, so a correction recorded only in `logs/` does not exist to the reader that matters most. Placing it under the transcript rather than in the body keeps the explanation next to the thing it explains, and collapsed keeps it out of the way of a human while remaining fully readable to a machine, which fetches block children regardless of collapse state.
- **Build impact:** `notion_output.build_correction_blocks()` + `_append_toggle()`; `create_meeting_page()` and `repair_meeting_page()` take a `corrections=` argument. ⚠️ **`None` and `[]` are deliberately different:** `[]` renders the toggle saying *"No term corrections were applied"*, `None` renders no toggle at all — silence must never mean both "nothing there" and "nobody looked". `pipeline.py` always passes a list, so the toggle is always present on a real run. The block also states plainly that the transcript above it is **not** raw speech-to-text and points at the uncorrected cache. 16 new assertions in `tests/test_notion_corrections.py` against a stubbed Notion client (0 failures), and the suite is proven able to fail: suppressing the toggle turns 3 red, collapsing the analysis grouping turns 2 red, restoring returns 16/16.

> **TL;DR —** The meeting page now carries a collapsed list of every word the pipeline swapped, sitting right under the transcript. The reviewer who reads these pages — and the automated step that consumes them — can see what was rewritten without going and finding a log file in a repository they never open.
